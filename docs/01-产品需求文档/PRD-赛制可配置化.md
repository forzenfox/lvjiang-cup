# 赛制可配置化功能 PRD

## 0. 术语表

| 术语 | 定义 |
| ---- | ---- |
| 赛制 | 一场赛事所采用的所有赛段规则的总称，如"16队瑞士轮晋级8强 + 单败淘汰赛"，可描述为一个结构化配置 |
| 赛程 | 由赛制推导出的具体比赛槽位集合（哪一轮、哪些队伍战绩组、用什么BO），即比赛对阵框架 |
| 战绩组 | 瑞士轮中拥有相同战绩（胜-负）的一批队伍构成的匹配池，如"1-0 组" |
| 晋级阈值 | 瑞士轮中达到该胜场数即晋级下一阶段的规则，如"3胜晋级" |
| 淘汰阈值 | 瑞士轮中达到该负场数即被淘汰的规则，如"3败淘汰" |
| 比赛槽位 | 一个待填写的比赛记录（对阵双方、轮次、战绩组、BO格式、状态），可被后续更新赛果 |
| 赛制模板 | 预置的可复用赛制配置，如"瑞士轮-16队"、"单败淘汰-8强"，模板本身可参数化 |
| BO1/BO3/BO5 | Best of 1/3/5，单场系列赛的对局数量 |

## 1. 产品概览

### 1.1 项目背景

当前驴酱杯赛事系统中，赛程展示与管理均围绕**一套固定的赛制**开发：

- 瑞士轮固定 **16 支队伍、3 胜晋级、3 败淘汰、固定 5 轮结构**
- 淘汰赛固定 **8 强 → 4 强 → 决赛** 单败结构
- 比赛槽位数量、轮次结构、晋级判定均以硬编码形式散落在前后端多个文件中

这意味着每次赛制变化（例如：16 队改成 8 队、3 胜制改成 2 胜制、淘汰赛改成双败）都需要**重新定制开发并发布**，导致：

1. **响应慢**：赛制决策需要留出开发排期，无法快速响应赛事运营需求
2. **成本高**：每次变化都是全新开发工作，且极易引入回归问题
3. **风险大**：展示端、槽位生成、晋级计算三处逻辑耦合，改一处容易漏一处
4. **不可复用**：无法沉淀"赛制"资产，下届赛事如果赛制不同，历史代码全部失效

因此需要用**配置化方式**将"赛制"从代码中解耦出来，使其成为一项可由运营者自由配置、系统自动生成赛程与判定结果的能力。

**设计原则：** 本需求的配置模型与"生成/渲染"机制必须按**可扩展的赛制体系**设计——未来新增赛制模式（如小组赛、双败淘汰、混合多段赛制）时，只能通过**新增赛制类型**接入，不得修改或推翻既有赛制类型的实现；赛制可描述为任意赛段的组合，而非写死的"瑞士轮 + 淘汰赛"两级。

### 1.2 目标用户

- **赛事运营者/管理员**：创建并维护赛制配置，生成赛程，管理比赛与晋级结果
- **赛事观众**：查看与当前赛制一致、结构正确的赛程展示
- **研发团队**：无需为赛制变化重复开发

### 1.3 产品价值

- **赛制自由化**：主流赛制（不同队伍数的瑞士轮、单败淘汰）无需开发即可生效；配置模型面向未来扩展，新赛制模式可通过新增赛制类型持续接入，避免重复设计
- **运营效率**：赛程槽位、晋级判定均由配置自动推导，减少人工维护
- **开发降本**：彻底消灭"赛制变更 = 定制开发"的重复劳动
- **历史数据安全**：新赛制不影响已办赛事的存档数据

### 1.4 业务目标

| 指标 | 当前值 | 目标值 | 测量周期 | 计算方式 | 目标依据 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| 赛制变更响应周期 | 需要定制开发（天级/周级） | 配置即可生效（分钟级） | 上线后首个新赛季 | 从确定赛制到赛程上线的时间 | 配置化后仅需运营填写表单 |

### 2.2 详细功能描述

#### 2.2.1 赛制配置模型

赛制配置是本次改造的**单一事实来源（Single Source of Truth）**，以 JSON 结构存储于后端，前端展示、槽位生成、晋级判定均只依赖该配置。

**模型设计要点（面向未来扩展）：**

1. **赛制 = 赛段序列**：一场赛事由 1..N 个赛段（Stage）按顺序组成，例如"瑞士轮 → 单败淘汰"。赛段之间通过**晋级出口**衔接（上一赛段晋级名单成为下一赛段参赛名单），天然支持任意赛段组合，不限于两级
2. **赛段类型化（可扩展枚举）**：每个赛段携带 `type` 标识。本期注册 `swiss`（瑞士轮）与 `elimination`（单败淘汰）两类；**未来新增赛制 = 新增一个 `type` 值**，每个类型自带独立的"槽位生成规则"与"展示渲染规则"，新增类型不得修改既有类型实现
3. **字段版本化**：配置带 `version` 字段，未来字段演进通过版本迁移兼容已保存的历史配置（扩展示例见附录 6.5）

**配置结构（产品级描述）：**

| 层级 | 字段 | 说明 | 取值示例 |
| ---- | ---- | ---- | ---- |
| 赛事配置 | version | 配置模型版本号，支持未来字段演进迁移 | 1 |
| 赛事配置 | name | 配置名称，运营者自定义 | "第三届 16队瑞士轮+8强" |
| 赛事配置 | stages[] | 赛段序列，顺序即赛程先后 | [瑞士轮赛段, 淘汰赛段] |
| 赛段（通用） | type | 赛段类型：swiss / elimination（可扩展枚举） | swiss |
| 赛段（通用） | name | 赛段展示名称 | "瑞士轮" |
| 赛段（通用） | teamCount | 进入该赛段的队伍数量 | 16 / 8 |
| 赛段（通用） | advanceToStage | 晋级出口（进入下一个赛段的下标；末段为空） | 1 |
| 赛段（瑞士轮特有） | qualifyRules | 晋级阈值（win）/ 淘汰阈值（loss） | win:3, loss:3 |
| 赛段（瑞士轮特有） | boRule | 轮次 BO 规则。auto（默认）= 逐场判定：该场比赛的胜者将达晋级阈值、或败者将达淘汰阈值时为 BO3，其余为 BO1（规则统一适用，不按队伍规模单独定义）；可整体覆盖为全 BO1 / 全 BO3 | auto / BO1 / BO3 |
| 赛段（淘汰赛特有） | stageNames | 各级阶段名称及各阶段 BO 格式 | 八强/半决/决赛 + BO3 |

**推导规则（产品规则，由系统自动计算，无需运营者填写）：**

- 瑞士轮总轮次 = 晋级阈值 + 淘汰阈值 - 1
- 每轮的战绩组 = 该轮可能出现的"胜-负"组合（如 3 胜制第 3 轮为 2-0 / 1-1 / 0-2）
- 退场规则：达到晋级阈值的队伍直接晋级、不再参加后续比赛；达到淘汰阈值的队伍直接淘汰退场；仅未达标队伍进入下一轮配对
- 某战绩组场次 = 组内队伍数 ÷ 2（同战绩组内随机配对）
- BO 自动规则：该场比赛的胜者将达晋级阈值、或败者将达淘汰阈值时为 BO3，其余为 BO1（该规则与现状 16 队 3 胜制后端各战绩组的 BO 分配完全一致；规则对任意规模统一适用——如 8 队 2 胜制下第 2 轮即为决定性比赛、为 BO3，无需按规模单独定义）
- 单败淘汰层级 = log2(淘汰赛队伍数)，从 1/4 决赛逐级递减到决赛
- 每场比赛的胜者进入次轮"胜场+1"战绩组，败者进入"负场+1"战绩组
- 下一赛段参赛名单 = 上一赛段晋级名单（经由晋级出口自动衔接）

#### 2.2.2 管理后台 - 赛制配置入口

**入口位置：** 管理后台侧边栏新增"赛制配置"菜单（或并入"赛程管理"页顶部），支持"新建/编辑"（P0）；"复制/删除"（P1）。

**创建流程：**

1. 运营者进入赛制配置页，点击"新建赛制"
2. 依次添加赛段：选择赛段类型（本期：瑞士轮 / 单败淘汰）→ 按类型填写参数（队伍数、晋级/淘汰阈值、BO 规则、阶段名称等）；**表单按赛段类型动态渲染**，未来新类型只需注册对应表单定义，无需改造配置页框架
3. 表单实时展示**预览**：各赛段推导出的轮次结构、每轮场次、槽位总数、赛段间晋级衔接
4. 点击"保存"，配置写入后端；点击"应用并生成赛程"，弹出确认框（提示将创建的槽位总数，**不覆盖已存在的比赛记录**）
5. 生成成功后可进入"赛程管理"继续填对阵与赛果

**约束校验（前端+后端双重校验）：**

| 校验项 | 规则 |
| ---- | ---- |
| 队伍数 | 只能为偶数，且满足"阈值约束"行的结构合法性判定 |
| 淘汰赛队伍数 | 必须为 2 的幂，且 ≤ 晋级名额、≥ 2 |
| 有瑞士轮时 | 晋级名额 = 淘汰赛队伍数（自动对齐，若用户先填淘汰赛规模则自动反推） |
| 无瑞士轮时 | 参赛队伍数 = 淘汰赛队伍数（直接单败开打） |
| 晋级名额约束 | 淘汰赛队伍数 ≤ 瑞士轮晋级队伍数 |
| 赛段衔接 | 后一赛段队伍数 ≤ 前一赛段晋级出口可提供的队伍数；末段无需出口 |
| 阈值约束 | 本期仅支持对称阈值：晋级阈值 = 淘汰阈值 ∈ {2, 3}。结构合法性由系统按推导公式自动判定（每个需比赛战绩组的队伍数必须为正偶数），无需人工查表；据此本期合法组合为：2 胜制 × 4/8/16/32 队，3 胜制 × 16/32 队（8 队 3 胜制因第 4 轮 2-1 组仅 3 队、奇数无法配对，不支持） |
| 赛段类型 | 仅允许已注册的类型；未注册类型在配置与表单中不可选（扩展机制见 2.2.1） |

#### 2.2.3 按配置生成赛程槽位

替换现有"初始化比赛槽位"的硬编码逻辑（当前写死 33 场瑞士轮 + 7 场淘汰赛）：

- 后端提供"按配置生成槽位"接口，入参为赛制配置（或配置 ID）
- 生成结果 = 纯函数推导：配置 → 槽位列表，槽位含 轮次/战绩组/BO 格式/排序序号/配置 ID 等元数据
- **槽位归属**：每条槽位写入生成时的配置 ID；存量无标识槽位按默认配置兜底
- 生成策略为**增量幂等**：仅创建不存在的槽位，已存在的记录（含赛果）不触碰；重复调用不产生重复槽位
- **覆盖式切换语义**：应用新配置并生成后，展示端与晋级计算仅取"当前生效配置"的槽位；旧配置槽位及赛果**保留但不展示**，切回原配置即可恢复查看
- 删除配置或修改配置后的生成，仅影响新增槽位；已录赛果的槽位保留（避免误删；如需重置提供独立"清空并重建"动作，二次确认）

**现状基准（评审确认）：**

- 后端 `initSlots` 现状实际生成 **33 场**瑞士轮（第 1~5 轮分别为 8+8+8+6+3 场）+ 7 场淘汰赛，"结构同现状"以此为准；管理后台"32 场"文案与后端代码注释"36 场"均为笔误
- 已知现状偏差：前端展示/编辑侧（swissTreeConfig、swissRoundSlots）将第 5 轮 2-2 组按 2 场配置，漏配第 3 场（按推导 2-2 组为 6 队 → 3 场）；本次改造统一以配置推导值（3 场）为准，属顺手修正现状展示缺陷

#### 2.2.4 展示端 - 瑞士轮赛制自适应

**现状：** 瑞士轮展示依赖固定 6 列布局与手写"槽位→晋级目标"映射（约 64 条键值对）。

**改造后：**

- 前端从后端获取当前赛制配置，瑞士轮树形图按配置动态生成：列数 = 轮次数，每列战绩组与场次 = 配置推导
- **晋级连线**由规则推导（胜者 → 胜场+1 组，败者 → 负场+1 组），不再手写映射
- 空槽位、晋级区（promotion）、淘汰区（elimination）的展示逻辑统一由配置驱动
- 快捷开关"BO1 视图 / BO3 视图"的列过滤逻辑按配置计算，而非固定列号

#### 2.2.5 展示端 - 淘汰赛自适应

- 淘汰赛对阵图按配置的层级数动态渲染（8 强 3 层、4 强 2 层、2 强 1 层）
- 阶段名称、Bracket 标签（quarterfinals/semifinals/finals 映射为配置中的名称与数量）自适应
- 连线（BracketConnector）按层级数量生成，不再写死三级

#### 2.2.6 晋级/淘汰自动计算参数化

**现状：** [advancementStore](file:///d:/File/workSpace/AI-test/lvjiang-cup/frontend/src/store/advancementStore.ts#L104-L114) 中 `wins === 3`、`losses === 3` 写死。

**改造后：**

- 晋级判定：`wins >= 晋级阈值` 即晋级；淘汰判定：`losses >= 淘汰阈值` 即淘汰
- **输入过滤**：晋级计算仅统计"当前生效配置"归属的瑞士轮已完赛比赛，避免旧配置槽位污染战绩
- 晋级名额：从配置取淘汰赛队伍数，缺省时按"达到阈值即全部晋级"
- 排序规则保持：晋级区胜场优先、败场少者靠前；淘汰区按胜场从少到多
- 若淘汰赛队伍数 < 达到阈值的队伍数，按排序截取前 N（并提示运营者复核）

#### 2.2.7 赛制配置查询接口

- 后端提供接口：获取/保存赛制配置；维护"当前生效配置"指针（切换即更新指针，指向目标配置 ID）
- 配置以**唯一 ID** 标识存储与寻址（为"多赛季/多配置隔离"独立需求预留主键结构，见 2.2.8）
- **比赛查询接口预留过滤参数**：`matches` 查询支持 `formatId` 参数（省略 = 当前生效配置）；本次前端统一按省略语义调用，避免独立需求实施后接口签名变化导致前端二次改造
- **NULL 兜底**：无 `formatId` 的存量槽位视为默认 16 队配置归属；未配置赛制的环境返回内置默认配置
- 首页展示端（Home/ScheduleSection）与管理后台共用同一配置数据源

#### 2.2.8 多赛季/多配置隔离（独立需求，另行立项）

**结论：** 该功能从本 PRD 拆出，作为**独立需求单独立项与排期，不属于本 PRD 交付范围**（评审结论）。

**边界划分（评估拆分影响后明确）：**

| 范围 | 内容 | 归属 |
| ---- | ---- | ---- |
| 最小打标机制 | 配置唯一 ID、槽位携带 formatId、比赛查询按 formatId 过滤、"当前生效配置"指针、NULL 兜底 | **本 PRD（P0）** —— 是覆盖式切换语义的前置闭环，也是独立需求的地基，不可省 |
| 完整多配置管理 | 多配置 CRUD 与列表、赛事/赛季维度建模、管理后台赛事切换 UI、首页赛季选择器 | **独立需求** —— 不在本 PRD 实施，避免范围蔓延 |

- **依赖关系**：独立需求应在本 PRD 的配置模型、槽位打标、展示渲染落地之后实施；本 PRD 顺势交付 formatId 与"当前生效配置"指针后，独立需求仅需补 UI 与多配置 CRUD，无需再改比赛数据结构与查询契约
- 本文档范围内采用"单配置 + 配置覆盖式切换"：应用新配置仅新增槽位，旧槽位保留但不展示（US-005 / AC-008 / AC-010）

## 3. 非功能需求

| 项 | 要求 |
| ---- | ---- |
| 兼容性 | 新版本发布后，未配置赛制的环境/历史数据按默认 16 队瑞士轮行为运行，不得报错或显示异常 |
| 数据迁移 | 存量无 formatId 槽位按默认配置兜底展示，无需人工迁移；新增 formatId 字段不影响既有查询契约 |
| 幂等性 | "生成槽位"可重复调用，不产生重复数据；不覆盖已填写的赛果 |
| 性能 | 32 队伍数上限下，配置预览与生成接口响应 < 500ms；前端渲染无卡顿 |
| 可维护性 | 删除全部硬编码的结构数据（槽位表、晋升映射、写死文案），统一收敛为配置驱动 |
| 可扩展性 | 新增赛制类型（如小组赛/双败）通过注册"生成规则 + 渲染规则"接入，不得修改既有 swiss/elimination 类型的实现；任一类型缺省时默认行为不回归 |
| 安全 | 赛制配置仅管理员可读写；遵循现有 JWT + admin 角色校验体系 |

## 4. 边界与假设

1. **P0 交付**：仅交付"瑞士轮（任意偶数队，2/3 胜制）+ 单败淘汰（2^n 队）"两类赛段类型；**但配置模型、槽位生成、展示渲染均按可扩展赛制体系设计**——小组赛、双败制、多段混合赛制等新赛制未来以"新增赛段类型"方式接入，无需推翻本设计（机制见 2.2.1，示例见附录 6.5）
2. **队伍数上限** 32（含）以内；瑞士轮仅 2/3 胜制（对称阈值）可选，合法组合以 2.2.2 判定式为准，其余阈值后续版本扩展
3. **配对规则**：瑞士轮同战绩随机配对，保留现有规则，不引入种子队/回避规则
4. 本文档范围采用**单配置模式**（"单配置 + 配置覆盖式切换"）；多赛季/多配置并存为独立需求（见 2.2.8），本 PRD 仅保留扩展点
5. 展示端不新增视觉样式，仅按配置重构结构与数据来源；视觉样式沿用现有 esports-theme
6. 赛事配置变更若发生在赛程已开始后，只影响新增槽位与展示结构，已录入赛果不因配置变化而丢失或改写
7. 淘汰赛槽位的对阵双方填充沿用现有流程与能力；本 PRD 仅参数化槽位结构、层级与渲染，不改变对阵填充方式，亦不涉及对阵自动填充（如需自动填充，后续独立评估）

### 6.3 瑞士轮推导示例（8 队 / 2 胜 2 败）

```
第1轮 (0-0)：4场 BO1
第2轮 (1-0)：2场 BO3（胜者 2-0 达晋级阈值，直接晋级）
第2轮 (0-1)：2场 BO3（败者 0-2 达淘汰阈值，直接淘汰）
第3轮 (1-1)：2场 BO3（胜者 2-1 晋级，败者 1-2 淘汰）
瑞士轮合计 10 场；2-0 / 0-2 组在进入第 3 轮前已达阈值退场，不产生比赛
晋级 4 队 → 淘汰赛 4 强：半决赛 2 场 + 决赛 1 场，共 3 场
```

BO 分配说明：8 队 2 胜制下第 2 轮起即为决定性比赛（胜负直接决定晋级/淘汰），按 BO 自动规则为 BO3，与 CS Major 等主流 8 队瑞士轮实践一致；早期示例中"第 2 轮 BO1"系沿用 16 队 3 胜制（第 2 轮非决定性、为 BO1）的惯性写法，已在评审中修正。

### 6.5 未来赛制扩展设计示例（验证模型扩展能力，本期不实现）

以"新增赛段类型"方式接入新赛制，接入前后**既有 swiss/elimination 的槽位生成、展示渲染、晋级判定代码零修改**，仅新增一个类型注册项。

**示例一：新增"小组赛（group）"赛段类型**

| 接入点 | 内容 |
| ---- | ---- |
| 类型枚举 | 新增 `type = "group"` |
| 类型特有字段 | `groups`（组数）、`teamsPerGroup`（每组队伍数）、`qualifyPerGroup`（每组晋级数） |
| 槽位生成规则 | 组内单循环：每组场次 = C(每组队伍数, 2)，槽位携带组别元数据 |
| 展示渲染规则 | 分组积分表 + 各组成绩/晋级标识 |
| 赛段衔接 | `advanceToStage` 指向下一赛段（如淘汰赛）；晋级名单 = 各组前 N 名 |

**示例二：新增"双败淘汰（double_elimination）"赛段类型**

| 接入点 | 内容 |
| ---- | ---- |
| 类型枚举 | 新增 `type = "double_elimination"` |
| 类型特有字段 | `dropToLosersRound`（败者组轮次衔接）、胜者组/败者组 BO 规则 |
| 槽位生成规则 | 胜者组/败者组双轨槽位生成，含重置(RESET)总决赛判定 |
| 展示渲染规则 | 双败对阵图（胜者组 + 败者组 + 总决赛） |

**示例三：混合多段赛制（验证赛段序列表达能力）**

```
赛事配置 = [
  赛段1: type=group      小组赛（4组×4队，每组前2晋级）
  赛段2: type=swiss      瑞士轮（8队，2胜2败）
  赛段3: type=elimination 单败淘汰（4强 → 决赛）
]
```

该示例说明：赛制 = 任意赛段的组合，仅通过 `advanceToStage` 衔接，扩展新赛制不推翻既有设计与数据。
