> 对应需求：[PRD-赛制可配置化.md](../01-产品需求文档/PRD-赛制可配置化.md)（v1.3，已通过评审）

## 1. 文档概述

### 1.1 文档目的

本文档基于《PRD-赛制可配置化.md》产品需求文档，提供详细的技术实现方案，指导开发团队进行系统设计、编码实现和测试验证。核心目标是：将散落在前后端的**硬编码赛制规则**（槽位清单、晋级映射、BO 分配、晋级阈值）统一收敛为**配置驱动的纯函数推导**，使赛制变更从"定制开发"变为"配置即生效"，同时保证配置模型对未来新赛制类型（小组赛、双败制等）的可扩展性。

### 1.2 适用范围

- **后端开发工程师**：format 配置模型与存储、槽位生成算法、matches 查询过滤、admin 接口
- **前端开发工程师**：视图模型推导算法、瑞士轮/淘汰赛动态渲染改造、管理后台配置页
- **测试工程师**：生成算法与晋级计算单测、默认配置回归、E2E 兼容性验证
- **运维工程师**：数据库迁移（matches.format_id 列）、部署与回滚

### 1.3 术语定义

参考 PRD §0 术语表，本文档使用相同术语定义。另补充内部技术术语：

| 术语 | 定义 |
| ---- | ---- |

## 3. 配置模型设计

### 3.1 设计原则

1. **配置是唯一事实来源**：槽位生成、视图推导、晋级计算均只依赖配置对象，不读任何硬编码常量
2. **前端与后端共享同一套配置结构定义**（分别维护 TS 类型，结构逐字段一致，用单测互相锁定）
3. **赛段类型化 + 注册表扩展**（后端生成器注册表 / 前端视图推导 switch），新类型只新增、不改旧
4. **字段版本化**：`version` 字段供未来迁移；本期 `version = 1`

### 3.2 TypeScript 类型定义（前后端一致）

```typescript
// —— 基础类型 ——
export type StageType = 'swiss' | 'elimination';
export type BoFormat = 'BO1' | 'BO3' | 'BO5';
export type SwissBoRule = 'auto' | 'all-bo1' | 'all-bo3';

// —— 瑞士轮赛段 ——
export interface SwissStageConfig {
  type: 'swiss';
  name: string;              // 展示名，如"瑞士轮"
  teamCount: number;         // 参赛队伍数（偶数，≤32）
  winThreshold: number;      // 晋级阈值（2 或 3）
  lossThreshold: number;     // 淘汰阈值（2 或 3，本期与 winThreshold 对称）
  boRule: SwissBoRule;       // BO 规则
  advanceToStage: number | null; // 晋级出口（下一赛段下标，末段为 null）
}

// —— 淘汰赛赛段 ——
export interface EliminationStageConfig {
  type: 'elimination';
  name: string;              // 展示名，如"淘汰赛"
  teamCount: number;         // 参赛队伍数（2 的幂）
  advanceToStage: null;      // 末段固定为 null
  roundNames: string[];      // 各级名称，从首轮到决赛，如["八强赛","半决赛","决赛"]
  boFormat: BoFormat;        // 各级统一 BO（本期不逐级配置）
}

export type StageConfig = SwissStageConfig | EliminationStageConfig;

// —— 赛制配置 ——
export interface FormatConfig {
  version: 1;
  name: string;              // 配置名称
  stages: StageConfig[];     // 赛段序列（1..N）
}
```

### 3.4 配置校验规则（前后端共用实现逻辑）

| 校验项 | 规则 | 归属 |
| ---- | ---- | ---- |
| 赛段序列 | 至少 1 个赛段；末段 `advanceToStage = null`；中间段指向下一段下标 | 通用 |
| 队伍数 | `teamCount` 为偶数且 4 ≤ n ≤ 32（淘汰赛为 2 的幂） | 通用 |
| 赛段衔接 | 后一赛段 `teamCount` ≤ 前一赛段晋级出口可供给数 | 通用 |
| 瑞士轮阈值 | `winThreshold = lossThreshold ∈ {2, 3}` | swiss |
| 瑞士轮结构合法性 | 推导后每个需比赛的战绩组内队数为正偶数（据 PRD：2 胜制支持 4/8/16/32 队；3 胜制支持 16/32 队，8 队 3 胜制因第 4 轮 2-1 组 3 队奇数不合法） | swiss |
| 淘汰赛结构合法性 | `teamCount` 为 2 的幂且 ≥ 2；`roundNames.length = log2(teamCount)` | elimination |

### 4.2 matches 表新增 format_id 列（迁移）

沿用现有 `PRAGMA table_info` + `ALTER TABLE ADD COLUMN` 迁移模式（参照 [migrateAuctionPrice](file:///d:/File/workSpace/AI-test/lvjiang-cup/backend/src/database/database.service.ts#L423-L435)）：

```typescript
private async migrateMatchFormatId() {

  const hasColumn = columns.some((col: any) => col.name === 'format_id');

    await this.run(`ALTER TABLE matches ADD COLUMN format_id TEXT`);

```

**NULL 语义**：`format_id IS NULL` = 迁移前遗留槽位，归属"内置默认配置"。无需数据回填（PRD 非功能需求"数据迁移：零人工迁移"）。

### 4.3 生效配置解析与槽位过滤规则（核心语义）

| 场景 | 生效配置 | matches 查询过滤（formatId 省略时） |
| ---- | ---- | ---- |
| 无任何激活配置（含全新安装） | 内置默认配置 | `WHERE format_id IS NULL` |
| 存在激活配置 X | 配置 X | `WHERE format_id = 'X'` |
| 显式传 formatId 参数 | 该配置 | `WHERE format_id = ?`，不传则按上表 |

推论：

- **AC-007 迁移兼容**：存量 NULL 槽位 + 无激活配置 → 生效配置恰为内置默认（与旧槽位结构一致）→ 展示与管理行为与发布前一致
- **AC-010 覆盖式切换**：激活 8 队配置后只显示新生成的 13 个槽位，NULL 旧槽位不混入；清除激活（切回默认）→ 旧槽位恢复可见
- **不自动"认领"**：显式配置生成槽位时，仅 `INSERT` 不存在的 id 并打上申请配置的 id；已存在 id（如旧 NULL 槽位）**不触碰、不改标**。因此新建显式 16 队配置会因槽位 id 全部冲突而"零新增"——这属预期行为，运营者如需按显式配置管理同结构赛程，应使用"清空并重建"（见 6.4）

### 4.4 槽位 id 生成规则（确定性、兼容现有数据）

槽位 id 保持与现状一致的确定性格式，保证默认配置路径下现有 E2E 夹具（`swiss-r1-1`、`elim-qf-1` 等）不变：

```
瑞士轮: swiss-r{轮次}-{组内序号}    例: swiss-r1-1 ~ swiss-r1-8, swiss-r5-1 ~ swiss-r5-3
淘汰赛: elim-{stageKey}-{序号}      例: elim-qf-1 ~ elim-qf-4, elim-sf-1, elim-f-1
```

> 注：现有代码第 5 轮 id 为 `swiss-r5-1..3`，第 1~4 轮为 `swiss-r{轮}-{战绩组缩写}{序号}`（如 `swiss-r2-h1`）。生成器按统一规则 `swiss-r{轮}-{序号}` 生成新槽位 id；**旧数据保留原 id，仅当 generate 遇到同 id 才跳过**。由于旧槽位按 NULL 归属、显式配置生成 id 与旧 id 部分不同，需在生成器中处理"结构与该配置一致的旧 NULL 槽位"的匹配问题——见 5.3.4 幂等匹配策略。

## 5. 核心算法设计

### 5.1 槽位生成器注册表（后端扩展点，满足 US-009 / AC-009）

```typescript
// generators/generator.registry.ts
export interface GeneratedSlot {
  id: string;
  round: string;              // 轮次名称
  stage: StageType;
  status: 'upcoming';
  // 瑞士轮特有
  swissRecord?: string;
  swissRound?: number;
  // 淘汰赛特有
  eliminationBracket?: string;      // 存 roundNames 对应阶段名（本期仍写 quarterfinals/semifinals/finals 兼容前端 Type）
  eliminationGameNumber?: number;
  boFormat: BoFormat;
}

export type SlotGenerator = (stage: StageConfig) => GeneratedSlot[];

export const SLOT_GENERATOR_REGISTRY: Record<StageType, SlotGenerator> = {
  swiss: generateSwissSlots,
  elimination: generateEliminationSlots,
};

export function generateAllSlots(format: FormatConfig): GeneratedSlot[] {
  return format.stages.flatMap(stage => SLOT_GENERATOR_REGISTRY[stage.type](stage));
}
```

**新增赛制类型 = 新增一个生成器函数 + 注册表加一行**，不修改既有生成器（AC-009 验收点）。

### 5.2 瑞士轮槽位生成算法（swiss.generator.ts）

```
输入: SwissStageConfig { teamCount, winThreshold, lossThreshold, boRule }
输出: GeneratedSlot[]

步骤:
1. 轮次数 = winThreshold + lossThreshold - 1
2. B 树结构推导（战绩组 → 队数）:
   - 初始: recordMap = { '0-0': teamCount }
   - 对每一轮 r (1..rounds):
     - 遍历 recordMap 中兵为需比赛的战绩组（wins < winThreshold 且 losses < lossThreshold 且队数 > 0）
     - 每组生成 matches = 队数 / 2 个槽位
     - 槽位 boFormat = resolveBo(record, winThreshold, lossThreshold, boRule)
     - 演进: 胜者进 (wins+1)-(losses) 组, 败者进 (wins)-(losses+1) 组; 达阈值队伍出树
   - 每轮结束后，将 map 中"已达标"的战绩组移除（不生成比赛）
3. 槽位 id 按轮内顺序编号
4. round 字段 = 轮次名（沿用 'Round N' 语义，展示层由前端视图模型赋予中文名）
```

**BO 自动规则（resolveBo，决定性比赛判定）**——PRD 2.2.1 定义的统一规则：

```typescript
function resolveBo(record, winThreshold, lossThreshold, boRule): BoFormat {
  if (boRule === 'all-bo1') return 'BO1';
  if (boRule === 'all-bo3') return 'BO3';
  // auto: 该场胜者将达晋级阈值 或 败者将达淘汰阈值 → BO3，否则 BO1
  const [wins, losses] = record.split('-').map(Number);
  const decisive = (wins + 1 >= winThreshold) || (losses + 1 >= lossThreshold);
  return decisive ? 'BO3' : 'BO1';
}
```

**推导结果对照（16 队 3 胜制，必须与现状 33 场一致）**：

| 轮次 | 战绩组（队数） | 场数 | BO |
| ---- | ---- | ---- | ---- |
| R1 | 0-0 (16) | 8 | BO1 |
| R2 | 1-0 (8), 0-1 (8) | 8 | BO1 |
| R3 | 2-0 (4) / 1-1 (8) / 0-2 (4) | 8 | BO3 / BO1 / BO3 |
| R4 | 2-1 (6), 1-2 (6) | 6 | BO3 |
| R5 | 2-2 (6) | 3 | BO3 |
| 合计 | - | **33** | - |

**8 队 2 胜制**：R1 0-0(8)=4 场 BO1；R2 1-0(4)+0-1(4)=4 场 BO3；R3 1-1(4)=2 场 BO3；合计 **10 场**（2-0/0-2 组达阈值退场不比赛）。与实际推导一致。

### 5.3 淘汰赛槽位生成算法（elimination.generator.ts）

```
输入: EliminationStageConfig { teamCount, roundNames, boFormat }
输出: GeneratedSlot[]

1. levels = log2(teamCount)            // 8 队 = 3 级
2. 对 level i (0..levels-1):
   - 场次数 = teamCount / 2^(i+1)      // 4, 2, 1
   - round = roundNames[i]
   - eliminationBracket = i===0 ? 'quarterfinals' : i===1 ? 'semifinals' : 'finals'
     （levels≠3 时映射策略见下）
   - eliminationGameNumber 连续编号（1..7）
   - boFormat = 配置值
```

**bracket 命名兼容策略**：`matches` 表存在 `elimination_bracket CHECK IN ('quarterfinals','semifinals','finals')` 约束（见 [database.service.ts](file:///d:/File/workSpace/AI-test/lvjiang-cup/backend/src/database/database.service.ts#L226-L231)）。本期不放松该 CHECK，映射规则：

- levels = 1（2 队）：仅决赛，`elimination_bracket = 'finals'`
- levels = 2（4 队）：首轮写 `quarterfinals`、次轮 `finals`（展示名由配置 `roundNames` 决定，不依赖 bracket 枚举）
- levels = 3（8 队）：`quarterfinals / semifinals / finals`（与现状一致）
- levels > 3（16 队，边界内）：首两轮映射 `quarterfinals`、最后一级 `finals`、其余写 `quarterfinals` 并依靠 `eliminationGameNumber` 区分（展示层按 `roundNames` 与编号排序渲染，不依赖 bracket 值）

### 5.4 槽位生成器（format-generator.ts）与幂等匹配策略

```typescript
async function generateSlots(formatId: string, format: FormatConfig) {
  const slots = generateAllSlots(format);
  // 幂等匹配：同生成 id 已存在 → 跳过（不覆盖、不改标）
  for (const slot of slots) {
    const existing = await db.get('SELECT id FROM matches WHERE id = ?', [slot.id]);
    if (existing) continue;                       // 已存在不触碰
    await db.run(`INSERT INTO matches (id, round, stage, status, format_id, swiss_record, ...) ...`, [...]);
  }
}
```

- 旧 NULL 槽位与显式配置生成 id 冲突时跳过 → 显式 16 队配置"零新增"属预期行为（见 4.3）
- 重复调用同一配置 → 全部跳过 → 幂等（AC-006）
