## 1. 什么是 Skill

Skill 是 SOLO 系统中 AI 大模型的**可执行指令集**。它不是一个给人阅读的方法论文档，而是一套**精确的、可执行的、带判断逻辑的指令**，指导 AI 在特定场景下如何思考、如何行动。

### Skill 与普通文档的区别

| 维度 | 普通文档 | Skill |
|------|---------|-------|
| 目标读者 | 人类开发者 | AI 大模型 |
| 指令粒度 | 原则性指导 | 精确的 step-by-step 指令 |
| 判断逻辑 | 人凭直觉判断 | 明确的分支条件和决策树 |
| 参考内容 | "够用就行" | 尽可能完整（AI 能全量处理） |
| 示例 | 1 个示例理解模式 | 多个示例覆盖不同场景 |
| 验证方式 | 人理解即可 | 过程合规性检查 |

### Skill 的定位光谱

```
纯思维方法 ←──────────────────────────────→ 固定解决方案

TDD              brainstorming     security        webapp-testing
│                │                 │              │
纯方法论          流程+模板         知识库+应用     脚本+工具链
无脚本            无脚本            无脚本          有脚本
铁律驱动          问题驱动          参考驱动        命令驱动
```

大多数 Skill 偏向"思维方法"一侧。Skill 的核心价值是**改变 AI 的思考方式**，而不是提供自动化工具。

## 2. Skill 设计哲学

### 2.1 AI 优先原则

Skill 是给 AI 用的，不是给人看的。这意味着：

```
❌ 给人看："检查测试环境配置是否正确"
✅ 给 AI 执行：
   1. 读取 vitest.config.ts 检查 environment 字段
   2. 读取 tests/setup.tsx 检查全局 mock
   3. 对每个 mock 执行风险评估（见 references/mock-risk-assessment.md）
   4. IF 发现高风险 mock → 建议替换为真实实现
```

### 2.2 思维方法 > 固定方案

Skill 应该教 AI **如何思考**，而不是提供标准答案。因为：

- 每个故障场景的技术栈、环境、依赖链都不同
- 固定方案无法覆盖所有场景
- 思维方法可以迁移到任何场景

```
❌ 固定方案："对于 React + jsdom 测试，执行以下 5 个步骤..."
✅ 思维方法："从断言回溯到环境，从上游到下游逐层验证"
```

### 2.3 精确指令原则

AI 没有"直觉"，需要明确的判断条件：

```
❌ 模糊指令："检查 DOM 是否正常"
✅ 精确指令：
   IF screen.debug() 输出包含目标组件 → 渲染层通过
   IF screen.debug() 输出为空 → 渲染层失败，回溯到环境层
   IF screen.debug() 输出有内容但缺少关键元素 → 检查数据层
```

### 2.4 完整参考原则

AI 没有"记不住"的问题。参考文档越全面，AI 在不同场景下的诊断就越准确。

```
❌ 给人看：每个陷阱 2-3 条，太多记不住
✅ 给 AI 用：每个环境 10+ 条常见陷阱，AI 能全部检索
```

## 3. 设计决策框架

创建 Skill 时，需要回答以下 5 个关键问题：

### Q1: 解决什么问题？

明确定义 Skill 的**适用领域**和**不适用领域**。

```
适用领域：
  - 前端组件测试调试（核心场景）
  - 后端集成测试调试
  - CI/CD 环境差异问题
  - 跨服务级联故障

不适用领域：
  - 纯算法/逻辑 bug
  - 已知类型的单点故障（拼写、类型）
  - 性能优化
  - 数据库查询优化
```

### Q2: 触发条件是什么？

定义**硬性条件**（必须全部满足）和**加权条件**（满足 N 项触发）。

```
硬性条件（全部必须满足）：
  - 依赖链深度 ≥ 3 层
  - 存在"修复后暴露新故障"的级联模式

加权条件（满足 ≥3 项触发）：
  - 环境差异（jsdom、CI vs 本地）
  - 多层 mock（≥2 层）
  - 多步状态转换
  - 条件渲染/守卫条件
  - 异步时序依赖
  - 闭包/缓存陈旧
  - 部分通过部分失败
```

### Q3: 思维方法还是固定方案？

判断 Skill 应该定位在哪一端：

| 判断标准 | 偏向思维方法 | 偏向固定方案 |
|---------|-------------|-------------|
| 场景可预测性 | 低（每次不同） | 高（重复性任务） |
| 核心判断 | 需要推理 | 可以自动化 |
| 技术栈依赖 | 跨技术栈 | 特定技术栈 |
| 变化频率 | 场景多变 | 稳定不变 |

### Q4: 需要什么参考文档？

根据 Skill 的复杂度决定：

- **简单 Skill**：仅 SKILL.md 即可
- **中等 Skill**：SKILL.md + 2-3 个 reference
- **复杂 Skill**：SKILL.md + references + templates

### Q5: 如何验收？

验收标准应该是**过程合规性检查**，而非结果正确性检查。

```
✅ 正确验收：
   "AI 是否按照 SKILL.md 的指令执行了每一步？"
   "AI 是否从上游开始逐层验证？"
   "AI 是否在每层做出了正确的分支判断？"

❌ 错误验收：
   "AI 的修复方案是否和预期一致？"
```

## 4. 文件结构与约定

### 标准目录结构

```
/data/user/skills/<skill-name>/
├── SKILL.md                          # 主文件（必需）
├── references/                       # 参考文档（可选）
│   ├── reference-1.md
│   └── reference-2.md
└── templates/                        # 模板文件（可选）
    ├── template-1.md
    └── template-2.md
```

### 文件命名约定

- `SKILL.md`：主文件名固定，使用大写
- `references/`：使用 kebab-case（`dependency-chain-mapping.md`）
- `templates/`：使用 kebab-case（`debug-report-template.md`）

### SKILL.md 文件头

每个 SKILL.md 必须以 YAML frontmatter 开头：

```yaml
---
name: <skill-name>
description: >
  <一句话描述技能用途和触发条件>
  <第二行补充说明>
---
```

示例：

```yaml
---
name: layered-debug
description: >
  Diagnose "layered failure cascade" bugs — where each fix reveals a deeper issue.
  Uses a structured 7-step process from environment layer to assertion layer.
  Trigger when user encounters circular debugging, environment-specific failures,
  or multi-layer dependency chain issues.
---
```

## 5. SKILL.md 编写指南

### 5.1 内容结构

```
1. 概述（Overview）
   - 技能解决什么问题
   - 核心原则（一句话）

2. 适用条件检查（Trigger Conditions）
   - 硬性条件清单
   - 加权条件清单
   - 不适用场景

3. 核心工作流（Workflow）
   - N 步流程，每步包含：
     a. 执行指令（精确的 step-by-step）
     b. 判断逻辑（IF/ELSE 分支）
     c. 输出格式

4. 决策树（Decision Tree）
   - 可视化分支逻辑
   - 常见场景的快速导航

5. 参考文档索引（References）
   - 列出 references/ 目录中的文件
   - 说明每个文件的用途

6. 模板索引（Templates）
   - 列出 templates/ 目录中的文件
   - 说明每个模板的用途

7. Worked Example（完整工作示例）
   - 一个完整的实战案例
   - 展示每一步的执行过程和输出
```

### 5.2 指令编写规范

**使用精确的指令语言**：

```
✅ 好的指令：
   "执行 screen.debug() 并检查输出中是否包含 'player-row-TOP'"
   "IF 包含 → 渲染层通过，进入 Step 4"
   "IF 不包含 → 渲染层失败，回溯到 Step 2"

❌ 不好的指令：
   "检查组件是否渲染"
   "看看 DOM 是否正常"
```

**使用明确的判断逻辑**：

```
✅ 好的判断逻辑：
   IF 条件 A AND 条件 B:
     → 执行操作 X
   ELSE IF 条件 C:
     → 执行操作 Y
   ELSE:
     → 执行操作 Z

❌ 不好的判断逻辑：
   "根据情况决定下一步"
   "如果合适的话可以尝试..."
```

**使用结构化的输出格式**：

```
✅ 好的输出格式：
   环境诊断结果：
   - 测试框架: [vitest/jest/other]
   - 环境限制: [jsdom/node/other]
   - Mock 风险: [高风险 mock 列表 / 无风险]
   - 结论: [通过/不通过]

❌ 不好的输出格式：
   "环境看起来没问题"
```

### 5.3 决策树编写规范

决策树应该覆盖最常见的分支场景：

```markdown
## 决策树

测试失败 →
  DOM 为空？
    ├── 是 → Step 3: 检查渲染层
    │        ├── 组件未挂载 → 检查路由/mock (Step 2)
    │        └── 组件挂载但内容空 → 检查数据层 (Step 4)
    │
    └── 否 → DOM 有内容但断言失败
             ├── 找不到元素 → 检查选择器 vs 实际 DOM
             ├── 找到多个元素 → 检查 CSS/hidden 类
             └── 文本不匹配 → 检查 exact 匹配 + 格式化逻辑
```

### 5.4 Worked Example 编写规范

Worked Example 是 Skill 的"验收测试用例"，应该：

1. **基于真实案例**：从实际开发中提炼
2. **展示完整流程**：从触发到修复的每一步
3. **标注关键决策点**：在每个分支处说明为什么选择这条路
4. **包含错误路径**：展示"如果走错了会怎样"

```markdown
## Worked Example: [案例名称]

### 背景
[描述问题场景]

### Step 1: 依赖链分析
[展示依赖链地图]

### Step 2: 环境层验证
[展示验证过程和发现]

### Step 3-N: 逐层验证
[每层展示：执行指令 → 观察结果 → 判断结论]

### 关键教训
[从案例中提炼的通用经验]
```

## 6. References 编写指南

### 6.1 内容定位

References 是 SKILL.md 的**知识扩展**，不是独立的方法论文档。它们应该：

- 提供 SKILL.md 中引用的**详细参考信息**
- 包含**多个技术栈**的示例（AI 能全量检索）
- 使用**表格和清单**等结构化格式

### 6.2 常见 Reference 类型

| 类型 | 内容 | 示例 |
|------|------|------|
| 操作指南 | 如何执行某个操作 | `dependency-chain-mapping.md` |
| 评估矩阵 | 如何评估风险 | `mock-risk-assessment.md` |
| 陷阱速查 | 常见问题及解决方案 | `common-pitfalls.md` |

### 6.3 编写规范

```
✅ 好的 Reference：
   ## jsdom 环境陷阱
   | 陷阱 | 表现 | 原因 | 解决方案 |
   |------|------|------|---------|
   | CSS 类无效 | hidden 类不隐藏元素 | jsdom 不计算 CSS | findAllByText + toBeGreaterThan(0) |
   | 事件系统差异 | fireEvent.click 不触发 | jsdom 事件模拟不完整 | 原生 .click() 或 userEvent |

❌ 不好的 Reference：
   ## jsdom 环境
   jsdom 有一些限制，需要注意。
```

## 7. Templates 编写指南

### 7.1 内容定位

Templates 是 AI **输出格式的规范**，不是给人填的表格。它们应该：

- 定义 AI 输出的**结构化格式**
- 包含**占位符说明**
- 提供**填充示例**

### 7.2 编写规范

```markdown
## 依赖链地图模板

```
断言: <断言语句>
  └── <组件/函数>: <说明>
       └── <状态/属性>: <说明>
            └── <事件/调用>: <说明>
                 └── <上游组件>: <说明>
                      └── <数据源>: <说明>
                           └── <mock/真实依赖>: <说明>
                                └── <测试环境>: <说明>
```

### 填充说明
- `<断言语句>`: 测试中失败的断言代码
- `<组件/函数>`: 断言直接依赖的组件或函数
- 每层缩进 2 个空格，用 `└──` 连接
```

## 8. 验收标准

### 8.1 验收原则

验收 Skill 的标准是**过程合规性**，而非结果正确性。

```
✅ 正确验收：
   "AI 是否按照 SKILL.md 的指令执行了每一步？"
   "AI 是否从上游开始逐层验证？"
   "AI 是否在每层做出了正确的分支判断？"

❌ 错误验收：
   "AI 的修复方案是否和预期一致？"
   "AI 是否输出了正确的答案？"
```

### 8.2 验收检查清单

```
[ ] 触发条件检查：
    [ ] 硬性条件定义清晰
    [ ] 加权条件可量化判断
    [ ] 不适用场景明确列出

[ ] 工作流检查：
    [ ] 每步有精确的执行指令
    [ ] 每步有明确的判断逻辑（IF/ELSE）
    [ ] 每步有结构化的输出格式
    [ ] 步骤按依赖链从上游到下游排列

[ ] 决策树检查：
    [ ] 覆盖最常见的分支场景
    [ ] 分支条件可操作（不依赖"直觉"）
    [ ] 每个分支指向明确的下一步

[ ] Reference 检查：
    [ ] 内容完整（AI 能全量检索）
    [ ] 使用结构化格式（表格、清单）
    [ ] 包含多技术栈示例

[ ] Worked Example 检查：
    [ ] 基于真实案例
    [ ] 展示完整 7 步流程
    [ ] 标注关键决策点
    [ ] 包含错误路径说明
```

### 8.3 验收方法

用 Worked Example 作为验收测试用例：

1. 将 Worked Example 中的问题场景作为输入
2. 观察 AI 是否按照 SKILL.md 的指令执行
3. 检查 AI 在每一步的决策是否正确
4. 确认 AI 没有跳过上游直接调试下游

## 9. 完整案例：layered-debug 技能设计

以下是用本指南设计 `layered-debug` 技能的完整过程记录。

### 9.1 问题定义

**解决的问题**："层级式故障级联"——修复一个 bug 后暴露另一个 bug 的循环调试困境。

**核心洞察**：故障是层层堆叠的，表层问题掩盖了深层问题。必须从上游到下游逐层突破。

### 9.2 设计决策

| 决策问题 | 答案 | 理由 |
|---------|------|------|
| 思维方法还是固定方案？ | 思维方法 | 调试场景不可预测，固定方案无法覆盖 |
| 需要脚本吗？ | 不需要 | 核心判断无法自动化，脚本太脆弱 |
| Reference 深度？ | 尽可能完整 | AI 能全量检索，越全面诊断越准 |
| 验收方式？ | 过程合规性检查 | 验证 AI 是否按指令执行，而非结果正确性 |

### 9.3 触发条件

**硬性条件**（全部必须满足）：
- 依赖链深度 ≥ 3 层
- 存在"修复后暴露新故障"的级联模式

**加权条件**（满足 ≥3 项触发）：
- 环境差异、多层 mock、状态转换、条件渲染、异步时序、闭包陈旧、部分通过

### 9.4 7 步工作流

| 步骤 | 层级 | 验证内容 | 核心指令 |
|------|------|---------|---------|
| Step 1 | - | 绘制依赖链地图 | 从断言回溯到环境 |
| Step 2 | L0 | 环境层 | 检查测试配置、mock 风险 |
| Step 3 | L1 | 渲染层 | screen.debug() 检查 DOM |
| Step 4 | L2 | 数据层 | 检查 mock 返回值、守卫条件 |
| Step 5 | L3 | 交互层 | 检查事件绑定、闭包 |
| Step 6 | L4-L5 | 断言层 | 检查选择器匹配、边界场景 |
| Step 7 | - | 回归验证 | 运行全量测试 |

### 9.5 文件结构

```
/data/user/skills/layered-debug/
├── SKILL.md
├── references/
│   ├── dependency-chain-mapping.md
│   ├── mock-risk-assessment.md
│   └── common-pitfalls.md
└── templates/
    ├── debug-report-template.md
    └── dependency-chain-template.md
```

## 10. 常见陷阱

### 陷阱 1：把 Skill 写成给人看的文档

```
❌ "检查测试环境配置是否正确"（太模糊）
✅ "读取 vitest.config.ts 的 environment 字段"（可执行）
```

### 陷阱 2：过度自动化

```
❌ 写一个脚本自动分析所有依赖链（太脆弱）
✅ 教 AI 如何手动分析依赖链（可迁移）
```

### 陷阱 3：参考文档太简略

```
❌ "jsdom 有一些限制"（太简略）
✅ 列出每个限制的表现、原因、解决方案（可操作）
```

### 陷阱 4：验收标准设成"结果正确"

```
❌ "AI 必须输出和我们相同的修复方案"（太僵化）
✅ "AI 必须按照指令从上游到下游逐层验证"（可检查）
```

### 陷阱 5：触发条件太宽泛

```
❌ "遇到调试问题就触发"（太宽泛，误触发多）
✅ 硬性条件 + 加权条件的组合判断（精确触发）
```
